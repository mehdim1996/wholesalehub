## ۱. مقدمه

### ۱.۱ هدف سند
این سند چشم‌انداز، دامنه و ذی‌نفعان پروژهٔ **عمده‌یار** را تعریف می‌کند. هدف آن ایجاد درک مشترک میان تیم توسعه، مشتری و ذی‌نفعان درباره «چه چیزی می‌سازیم، برای چه کسی، و چرا» است.

این سند **قرارداد رسمی** نیست، بلکه **مرجع راهنما** برای تصمیم‌گیری‌های بعدی در طول چرخهٔ حیات پروژه است و در هر Sprint بازبینی می‌شود.

### ۱.۲ دامنهٔ سند
- **در دامنه:** اهداف کسب‌وکار، کاربران هدف، محدودهٔ MVP، معیارهای موفقیت، ریسک‌های سطح بالا.
- **خارج از دامنه:** جزئیات فنی، طراحی UI، نیازمندی‌های دقیق functional (که در SRS می‌آید).

### ۱.۳ تعاریف و اصطلاحات
| اصطلاح | تعریف |
|--------|--------|
| **MVP** | Minimum Viable Product — کمینهٔ محصول قابل ارائه |
| **User Story** | توصیف نیازمندی از دید کاربر |
| **Persona** | نمایندهٔ فرضی کاربر هدف |
| **Sprint** | بازهٔ کوتاه توسعه (۲-۳ هفته) در Scrum |
| **DoD** | Definition of Done — معیار «تمام‌شده» بودن کار |
| **ویزیتور** | فروشنده‌ای که به‌صورت حضوری به مشتریان مراجعه می‌کند |
| **تاریخ انقضا** | تاریخی که پس از آن فروش یا مصرف محصول مجاز نیست |
| **FEFO** | First Expired, First Out — خروج اول کالایی که زودتر منقضی می‌شود |
| **منطقه** | محدودهٔ جغرافیایی فروش (شهر، محله یا مسیر ویزیت) |

## ۲. چشم‌انداز محصول

### ۲.۱ بیانیهٔ چشم‌انداز (Vision Statement)

> **برای** صاحبان فروشگاه‌ها و پخش‌های عمده‌فروشی **که** مشتریان زیادی دارند اما مشتریان، سفارش‌ها و موجودی انبار را با دفتر و اکسل مدیریت می‌کنند،
> **عمده‌یار** یک **سامانهٔ مدیریت تحت وب** است
> **که** مدیریت مشتریان، یادآوری ویزیت، تحلیل فروش و انبارداری با پیگیری تاریخ انقضا را در یک‌جا فراهم می‌کند.
>
> **برخلاف** نرم‌افزارهای حسابداری سنگین و گران که پیچیده‌اند و روی مدیریت مشتری و انبار تمرکز ندارند،
> **محصول ما** ساده، سبک و متمرکز بر نیازهای روزمرهٔ عمده‌فروش است.

### ۲.۲ ارزش پیشنهادی (Value Proposition)

| برای | ارزش |
|------|-------|
| **مدیر / صاحب فروشگاه** | شناخت بهتر مشتریان، تصمیم‌گیری بر پایهٔ داده، جلوگیری از ضرر کالای منقضی |
| **ویزیتور** | دانستن اینکه به چه کسی و چه زمانی مراجعه کند، دیدن سابقهٔ خرید پیش از ویزیت |
| **انباردار** | ثبت دقیق موجودی و تاریخ انقضا، هشدار کالاهای نزدیک به انقضا |

### ۲.۳ مزیت رقابتی
- **سادگی:** رابط کاربری ساده‌تر از نرم‌افزارهای حسابداری
- **تمرکز:** مدیریت ارتباط با مشتری و انبار در کنار هم
- **تحلیل منطقه‌ای:** دیدن اینکه کدام محصول در کدام منطقه بهتر فروش می‌رود
- **پیشگیری:** هشدار انقضا و یادآوری ویزیت، پیش از وقوع ضرر یا از دست رفتن مشتری

## ۳. مشکل و فرصت

### ۳.۱ مشکل فعلی (Problem Statement)
صاحبان فروشگاه‌های عمده‌فروشی با چالش‌های زیر روبه‌رو هستند:
1. **پراکندگی اطلاعات مشتری:** لیست مشتریان در دفتر، اکسل یا حافظهٔ ویزیتورها است.
2. **ندانستن ارزش مشتریان:** مشخص نیست کدام مشتری بیشترین خرید را دارد.
3. **فراموش‌شدن ویزیت:** مراجعهٔ مجدد به مشتریان بر پایهٔ حافظه است و مشتریان غیرفعال از دست می‌روند.
4. **نبود تحلیل فروش:** مشخص نیست کدام محصول در کدام منطقه پرفروش است.
5. **ضرر ناشی از انقضا:** تاریخ انقضا ثبت یا پیگیری نمی‌شود و کالا در انبار منقضی می‌شود.
6. **موجودی نامطمئن:** شمارش دستی انبار پرخطا و زمان‌بر است.

### ۳.۲ فرصت (Opportunity)
- بسیاری از عمده‌فروشی‌ها هنوز دیجیتال نشده‌اند یا فقط از اکسل استفاده می‌کنند.
- نیاز به نرم‌افزار ساده و ارزان‌تر از سیستم‌های ERP.
- امکان تصمیم‌گیری بهتر با داده‌هایی که همین حالا هم تولید می‌شوند اما استفاده نمی‌شوند.
- کاهش ضرر مالی با مدیریت تاریخ انقضا.

## ۵. محدودهٔ محصول

### ۵.۱ داخل محدوده (In Scope — MVP)

**کاربری (Functional):**
- **F-01** مدیریت مشتریان (افزودن، ویرایش، حذف، جست‌وجو) همراه با اطلاعات تماس و منطقه
- **F-02** ثبت سفارش و خرید برای هر مشتری
- **F-03** نمایش تاریخچهٔ خرید هر مشتری و بیشترین خرید او (محصول و مبلغ)
- **F-04** رتبه‌بندی مشتریان بر اساس حجم خرید
- **F-05** تنظیم و نمایش یادآوری مراجعهٔ مجدد (ویزیت) بر اساس بازهٔ زمانی یا تاریخ دلخواه
- **F-06** هشدار مشتریان بدون خرید در یک بازهٔ مشخص
- **F-07** داشبورد تحلیل فروش: پرفروش‌ترین محصولات در هر منطقه
- **F-08** گزارش‌های فروش بر اساس بازهٔ زمانی، منطقه و محصول (جدول و نمودار)
- **F-09** مدیریت محصولات و موجودی انبار (ورود و خروج کالا)
- **F-10** ثبت تاریخ انقضا و شمارهٔ بچ برای هر ورودی کالا
- **F-11** هشدار کالاهای نزدیک به انقضا و منقضی‌شده
- **F-12** هشدار کمبود موجودی
- **F-13** مدیریت کاربران و نقش‌ها (مدیر، ویزیتور، انباردار)

**غیرکاربری (Non-functional):**
- **NF-01** زمان بارگذاری صفحه < ۲ ثانیه
- **NF-02** پشتیبانی از ۵۰ کاربر همزمان
- **NF-03** رابط کاربری واکنش‌گرا (Responsive)، به‌ویژه برای موبایل ویزیتورها
- **NF-04** رمزنگاری گذرواژه‌ها (bcrypt) و کنترل دسترسی بر اساس نقش
- **NF-05** پشتیبانی از زبان فارسی، RTL و تاریخ شمسی
- **NF-06** امکان تهیهٔ نسخهٔ پشتیبان از داده‌ها

### ۵.۲ خارج از محدوده (Out of Scope)

| مورد | دلیل |
|------|-------|
| سیستم حسابداری کامل (دفتر کل، مالیات) | پیچیدگی بالا و خارج از توان یک ترم |
| پرداخت آنلاین | نیاز به مجوز و زیرساخت |
| پورتال ورود مشتریان برای ثبت سفارش | تمرکز روی استفادهٔ داخلی |
| اپلیکیشن موبایل بومی | تمرکز روی وب |
| نقشهٔ جغرافیایی و مسیریابی ویزیتور | منطقه فقط یک فیلد دسته‌بندی است |
| اسکن بارکد | اولویت پایین |
| ارسال خودکار پیامک | هزینه و وابستگی به سرویس بیرونی؛ یادآوری فقط داخل سامانه |
| چند شعبه‌ای | افزایش پیچیدگی |

### ۵.۳ محدودیت‌ها (Constraints)
- **زمانی:** ۱۴ هفته، ۳ Sprint
- **تیمی:** ۳-۴ نفر
- **فنی:** بدون سرور اختصاصی، استقرار روی سرویس ابری رایگان
- **بودجه:** صفر (فقط ابزارهای رایگان)

## ۸. رویکرد و متدولوژی

### ۸.۱ متدولوژی
- **Scrum سبک‌شده:** ۳ Sprint دو-سه هفته‌ای
- **ابزار مدیریت:** GitHub Projects
- **جلسات:** Sprint Planning، Daily (کوتاه، آنلاین)، Review، Retrospective

### ۸.۲ فناوری پیشنهادی
| لایه | فناوری |
|------|--------|
| Backend | Node.js + Express |
| Frontend | React + کتابخانهٔ نمودار (مثل Recharts) |
| Database | PostgreSQL |
| Version Control | Git + GitHub |
| CI/CD | GitHub Actions |
| مستندسازی | Markdown در GitHub |

### ۸.۳ Definition of Done
یک Story وقتی «تمام» است که:
1. کد نوشته و Merge شده باشد.
2. تست Unit برای آن نوشته شده باشد.
3. Code Review شده باشد.
4. مستندات مربوطه به‌روز شده باشد.
5. در محیط Demo کار کند.
